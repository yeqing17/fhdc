## 2. 本轮新发现

### 2.1 【P3】日志面板的空态文案在"有数据但被过滤光"时会误导

- **位置**:`apps/fhdc-desktop/src/panels/hilog.rs`(`visible_len == 0` 分支)
- **现象**:日志已经攒了几百行,用户在过滤框里敲一个匹配不到的词,面板会显示:

  ```
  已缓冲 512 行
  ［ 等待日志… ］
  ```

  两句话互相矛盾 —— 日志就在那儿,只是被过滤掉了。
- **原因**:空态只判断了可见行数为 0,没有区分"还没收到数据"和"数据被过滤光"。
- **改法**:按 `self.lines.is_empty()` 分三种文案:

```rust
let hint = if !self.lines.is_empty() {
    "当前级别/关键字下没有匹配的日志行"
} else if self.running {
    "等待日志…"
} else {
    "点击「开始」抓取设备日志"
};
```

### 2.2 【P3】"乐观置位 + 命令被丢弃"这条路仍然没有回收

- **位置**:`runtime.rs:74` `RuntimeBridge::try_send` + `panels/overview.rs:45`、`panels/applications.rs:68`、`panels/screenshot.rs:85`
- **现象**:概览/应用/截图三个面板的「刷新/拍照」按钮在 `loading == true` 时是禁用的。如果那条命令在 `try_send` 里被丢掉(命令队列 64 满),面板会**永久停在"读取中"且按钮不可点** —— 和第一次扫描里 1.1/1.2 是同一类失败模式,只是入口不同。
- **原因**:三个面板都是"发命令之前先置位 `loading`"(这个方向是对的,防重复请求),但 `try_send` 丢弃命令时返回 `()`,调用方无从知道,而唯一能重试的按钮又被 `loading` 禁用。设备切换会重置(1.1 的修复),所以能自愈,但那一刻面板是死的。
- **触发条件**:`command_tx` 容量 64,后端循环每次只取一条。hdc 卡在 8 秒超时里、用户又猛点按钮时才可能积满 —— **很罕见**,不是"现在就会踩到"的问题。
- **改法**:让丢弃可观测,一次解决三个面板:

```rust
// runtime.rs
pub fn try_send(&self, command: BackendCommand) -> bool {
    ...
    match self.command_tx.try_send(command) {
        Ok(()) => true,
        Err(_) => {
            tracing::warn!("后端命令队列已满,命令被丢弃");
            false
        }
    }
}
```

调用方(`overview.rs` / `applications.rs` / `screenshot.rs`)在返回 `false` 时把 `loading` 复位,并可以顺手弹一个 toast。改动约 10 行,把这一类"乐观置位没有回收路径"的风险一次性堵死。

> 说明:这不是代码现在有 bug,而是**同一类失败模式的最后一条未封的路径**。如果觉得收益不值,可以不动 —— 六轮下来这一类问题已经从"必然踩到"降到"极端时序"。

### 2.3 【NIT】回归测试的输入比真实分片小

- **位置**:`panels/shell.rs` `large_chunks_still_get_stripped`
- **现状**:`600 × "\x1b[32mA\x1b[0m\r\n"` = 7200 字节,断言是 `big.len() > 8192 / 2`(即 > 4096)。
- **问题**:7200 字节确实能拦住"按 4096 短路"的旧 bug,但**小于真实的单块分片 8192 字节**,而注释写的是"底层单块分片 8KB"。如果将来有人把 `ANSI_PENDING_LIMIT` 调到 8192,这个测试仍然通过,但线上真实分片正好命中阈值。
- **改法**:把循环次数提到 700(`8400` 字节),断言改成 `big.len() >= 8192`。一行的事。
