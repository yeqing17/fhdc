## 1. 必修项

### 1.1 切设备瞬间概览面板永久卡死

- **位置**:`apps/fhdc-desktop/src/panels/overview.rs` `reset_for`
- **现象**:正在加载概览时切到另一台设备,概览页永远停在"尚未读取设备信息",「刷新」按钮是灰的,重新选中设备也不会恢复,只能重启应用。
- **原因**:`reset_for` 没有复位 `loading`。而 `loading` 只由"target 匹配"的事件清除(`OverviewLoaded` / `OverviewFailed`),切设备后旧事件 target 不匹配,于是 `loading` 永远是 `true`;`wants_load` 要求 `!loading`,`refresh_enabled` 也要求 `!loading`,两条路都被堵死。

```diff
     pub fn reset_for(&mut self, target: Option<DeviceTarget>) {
         if self.target.as_ref() == target.as_ref() {
             return;
         }
         self.target = target;
         self.loaded = None;
         self.error = None;
+        // 旧 target 的加载事件不会再匹配,必须在这里复位,否则永久卡在 loading。
+        self.loading = false;
     }
```

### 1.4 概览页重复发请求

- **位置**:`apps/fhdc-desktop/src/panels/overview.rs`(`wants_load` / `load_command`)、`apps/fhdc-desktop/src/app.rs`(`auto_behaviors`)
- **现象**:每次进入概览页,后端会收到不止一条 `LoadOverview`。每条会串行执行 10 次 hdc 调用(型号、品牌、系统版本、API、内核、CPU、meminfo、df……),等于白跑好几倍的进程。
- **原因**:`wants_load` 用 `!self.loading` 去重,但 `loading` 要等 `OverviewLoading` 事件回来才置位。`auto_behaviors` 每帧问一次,事件回来之前的每一帧都会再发一条。对比 `files.rs` / `applications.rs` 的写法:它们都是"发命令之前先置位",唯独概览漏了。
- **改法**:把两个方法合并成一个会置位的 `maybe_auto_load`,与其它面板保持一致。

```diff

+        if !ctx.online() || self.loaded.is_some() || self.error.is_some() || self.loading {
+            return None;
+        }
+        let target = ctx.target.clone()?;
+        self.loading = true;
+        Some(BackendCommand::LoadOverview(target))
+    }
```

### 1.5 插拔设备不会自动发现

- **位置**:`apps/fhdc-desktop/src/app.rs`(字段 `last_device_refresh`、方法 `auto_behaviors`)
- **现象**:必须手点「⟲ 刷新设备」。USB 插上、网络设备断开、`hdc kill` 之后,界面都不会自己变。
- **原因**:`last_device_refresh` 只在 `EndpointConnect*` / `EndpointDisconnected` / `ServerKilled` 三个事件里被赋 `None`,**从来没有被读过**。看起来是"定时轮询"做了一半没接上。

```diff

         let ctx = self.panel_ctx();
+
+        // 设备轮询。上面三处事件把 last_device_refresh 置 None,正好触发一次立即刷新。
+        let refresh_due = self
```

### 1.6 设备下拉列表顺序随机抖动

- **位置**:`crates/fhdc-device/src/lib.rs` `snapshot()`
- **现象**:每次「刷新设备」,下拉框里的设备顺序可能变。设备一多很难点。
- **原因**:`records` 是 `HashMap`,`.values()` 的迭代顺序由随机种子决定,每次进程/每次快照都不保证一致。

### 1.8 终端 ↑↓ 翻历史方向反了

- **位置**:`apps/fhdc-desktop/src/panels/shell.rs` `show()` 里的历史翻阅块
- **现象**:按一下 ↑ 拿到最新一条命令,再按 ↑ 没有反应;按 ↓ 反而往回翻。
- **原因**:`history[0]` 是最旧的、`history[len-1]` 是最新的。↑ 应该减小下标,代码里写成了 `(index + 1)`。

```diff

+                    let last = self.history.len().saturating_sub(1);
                     let next = if down {
-                        index.saturating_sub(1)
+                        (index + 1).min(last)      // ↓ 往新的翻
                     } else {
-                        (index + 1).min(self.history.len() - 1)
+                        index.saturating_sub(1)    // ↑ 往旧的翻
                     };
                     self.history_cursor = Some(next);
                     self.input = self.history[next].clone();
                 }
```

> `saturating_sub` 同时修掉了 `self.history.len() - 1` 在空历史时的下溢风险(目前靠"cursor 为 Some 时历史必非空"的隐式约定才没炸)。

### 1.9 中文输出跨分片出现「�」

- **位置**:`apps/fhdc-desktop/src/panels/shell.rs` `append_bytes`、`apps/fhdc-desktop/src/panels/hilog.rs` `ingest`
- **现象**:终端和日志里偶发一个 `�`。如果你输出的是纯英文,看一辈子也碰不到;中文日志多了就会遇到。
- **原因**:底层按 8192 字节读写(`process.rs` 的 `CHUNK_BYTES`),一个 3 字节的汉字正好跨块时,`String::from_utf8_lossy` 会把前后两半各替换成一个 `�`,且不可逆。hilog 里的 `pending` 只缓存了"半行",没缓存"半个字符"。
- **改法**:在 `panels/mod.rs` 加一个增量解码函数,两个面板共用。

```diff
 apps/fhdc-desktop/src/panels/mod.rs
 /// 面板统一返回待发送命令。
 pub type Commands = Vec<BackendCommand>;
+
+/// 增量 UTF-8 解码:把跨分片被截断的多字节字符留到下一次,避免出现「�」。
+/// `pending` 由调用方持有,初始为空。
+pub fn decode_incremental(pending: &mut Vec<u8>, bytes: &[u8]) -> String {
+    pending.extend_from_slice(bytes);
+    match std::str::from_utf8(pending) {
+        Ok(text) => {
+            let text = text.to_owned();
+            pending.clear();
+            text
+        }
+        Err(error) => {
+            let valid = error.valid_up_to();
+            let text = String::from_utf8_lossy(&pending[..valid]).into_owned();
+            // error_len() == None 说明只是"尾巴被截断",留着等下一片;
+            // Some(n) 说明是真正的非法字节,跳过它,避免 pending 无限增长。
+            let skip = error.error_len().unwrap_or(0);
+            pending.drain(..valid + skip);
+            text
+        }
+    }
+}
```

### 1.12 终端整块缓冲每次输出全量重排

- **位置**:`apps/fhdc-desktop/src/panels/shell.rs:279`
- **现象**:终端输出一多就明显掉帧,`hilog` 那种持续刷的日志尤其明显。
- **原因**:`ui.label(self.buffer.clone())` 把整个 256KB 缓冲当成**一个** Label:
  1. 每帧都要 `clone` 一份 256KB + 计算排版缓存键(egui 内部按文本哈希缓存 galley);
  2. 每来一段输出文本就变了,缓存必然失效,于是**整个 256KB 全量重排**,一秒钟可能重排十几次。
- **改法(最小)**:只渲染尾部窗口(比如最后 2 万个字符),滚动区仍然吃 `stick_to_bottom`。

```diff

                     } else {
-                        ui.label(self.buffer.clone());
+                        // 只渲染尾部:整块 256KB 每次输出都会触发全量重排。
+                        ui.label(tail_chars(&self.buffer, MAX_RENDERED_CHARS).to_owned());
                     }
```

```diff
 /// 回显缓冲上限(字节)。
 const MAX_BUFFER_BYTES: usize = 256 * 1024;
+/// 单帧最多渲染的字符数(尾部窗口)。
+const MAX_RENDERED_CHARS: usize = 20_000;
```

```rust
/// 取字符串末尾 max_chars 个字符,按字符边界切片。
fn tail_chars(text: &str, max_chars: usize) -> &str {
    let mut count = 0;
    let mut start = 0;
    for (index, _) in text.char_indices().rev() {
        count += 1;
        if count > max_chars {
            return &text[start..];
        }
        start = index;
    }
    &text[start..]
```

## 2. 性能项

### 2.1 hilog 每帧全量过滤

`apps/fhdc-desktop/src/panels/hilog.rs` `show()` 每帧都干这些事:遍历最多 10000 行、对每行 `to_lowercase()` 分配一个新字符串、再收集一遍 `Vec<usize>`。只要过滤框里有内容,开启日志就会吃满一个核。

**改法**:把 `visible: Vec<usize>` 缓存进状态,用脏标记失效。

```rust
// HilogState 新增
visible: Vec<usize>,
visible_dirty: bool,

// 失效时机:ingest 追加了行、点「清空」、级别下拉框 changed、
// 过滤框 search.changed()、reset_for。
// show() 里:
if self.visible_dirty {
    let min_level = LEVELS[self.level_index];
    let query = self.query.to_lowercase();
    self.visible = self.lines.iter().enumerate()
        .filter(|(_, line)| { /* 同现有逻辑 */ })
        .map(|(index, _)| index)
        .collect();
    self.visible_dirty = false;
}
```

同类:文件列表 `files.rs:276` 和进程列表 `processes.rs:135` 也是每帧 `clone` + 全量 `sort`。同样的思路:排序结果缓存进状态,在 `entries` / `processes` 更新或排序键变化时重算。

### 2.2 后端命令循环里同步 await 网络类命令

`apps/fhdc-desktop/src/runtime.rs`:主循环里 `ConnectEndpoint`(tconn)、`DisconnectEndpoint`、`EnableTcpListen`、`KillServer`、`ClearDeviceHilog` 都是直接 `.await`,期间**整个命令队列停摆**。tconn 连一个不存在的 IP 时要等到 8 秒超时(`DEFAULT_TIMEOUT`),这 8 秒里点任何按钮都没反应。

**改法**:这些命令同样丢进 `tokio::spawn`,完成后通过现有的 `done_rx` 通道回传。把 `done_rx` 的元素从 `OperationId` 扩成枚举即可,`registry` 仍然只由主循环持有:

```rust
enum Completion {
    TransferDone(OperationId),
    /// 命令执行完且可能改变了设备列表 → 主循环里做一次 refresh_devices。
    RefreshDevices,
}
```

任务结束时发 `Completion::RefreshDevices`,主循环在 `done_rx.recv()` 分支里 `refresh_devices(...).await`。这样 `&mut registry` 不用跨任务传递,队列也不会被阻塞。

### 2.3 概览 10 次串行 hdc 调用

`crates/fhdc-hdc/src/lib.rs` `device_overview` 里 10 个 `self.probe(...).await` 依次执行,每次都是一个新的 `hdc` 进程(Windows 上进程创建本身就不便宜)。

**改法**:两条路,按喜好选。
- 简单:`tokio::join!` 并发跑(需要把 `self` 的借用变成多个独立 future,`probe` 已返回拥有所有权的 `Option<String>`,可行)。
- 更好:设备端合并成**一条** `sh -c '...'` 脚本,一次往返把所有字段打出来,再用现在的分隔符解析模式切分。注意别被 `probe` 的"失败返回 None"语义带偏:合并后要么整体成功,要么逐段容错。

## 5. 需要真机确认的一个假设

`crates/fhdc-hdc/src/files.rs` 的 `LIST_SCRIPT` 用 `\x1c`(FS)做字段分隔、`\x0`(NUL)做记录分隔,并且靠 `printf '\x1c'` 输出。

两个风险点,**假后端不会跑到这段脚本**,所以现有测试覆盖不到:

1. `\x1c` 不是 POSIX 标准写法(POSIX 是 `\034` 八进制)。OpenHarmony 上是 mksh + toybox,大概率支持,但值得实测一次。
2. 更关键的是 NUL 作为记录分隔符:如果输出经过 pty,NUL 可能被吞掉,那时候 `parse_directory_entries` 会把整个输出当成一条记录,表现就是**文件面板永远是空的**。

建议:真机连一次,先跑

```sh
hdc -t <key> shell "sh -c '<LIST_SCRIPT 原文>' fhdc-files /data/local/tmp" | Format-Hex
```

看输出里是否真有 `0x1C` 和 `0x00`。如果没有,改成八进制 `\034` + 换行分隔,并对文件名里的换行做 base64 编码(或者干脆用 `find -print0` 的 NUL 方案,前提是 NUL 能活下来)。
