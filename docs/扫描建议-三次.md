## 2. 本轮新发现

### 2.1 【P1】切设备后进程表显示上一台设备的进程,并且能对它执行 kill

- **位置**:`apps/fhdc-desktop/src/panels/processes.rs:46`(`reset_for`)+ 本轮新增的 `display_cache`
- **现象**:关掉「自动刷新(3 秒)」后切换设备,**进程表还是上一台设备的列表**,而且点「结束进程确认 → 结束进程」,`kill <pid>` 会发到**当前选中的新设备**上。
- **原因**:本轮把显示列表改成了缓存,失效键是 `(processes_generation, sort_key, sort_descending, query)`。但 `reset_for` 只清了 `processes`,没有清缓存、也没有让 `processes_generation` 递增:

```rust
self.target = target;
self.processes.clear();     // ← 数据清了
self.error = None;
self.last_refresh = None;
self.kill_prompt = None;
self.loading = false;       // ← 缓存没清,键也没变
```

`show()` 里键没变就不重算,于是继续借用旧的 `display_cache`。开着自动刷新时会在 200ms 左右被一次新加载盖掉(不易察觉);关掉自动刷新时 `tick()` 直接返回 `None`,这张表就**一直停在上一个设备**。

- **改法**:在 `reset_for` 里让缓存失效(和 `files.rs` 的 `reset_for` 保持一致):

```diff
         self.target = target;
         self.processes.clear();
+        // 缓存必须一起失效:否则切设备后仍显示上一台设备的进程表,
+        // 而"结束进程"会把旧 PID 发到新设备上。
+        self.display_cache.clear();
+        self.display_cache_key = None;
+        self.processes_generation += 1;
         self.error = None;
         self.last_refresh = None;
         self.kill_prompt = None;
         self.loading = false;
```

- **验收**:关掉自动刷新 → 在设备 A 打开进程页 → 切到设备 B → 表格应立即为空(或立刻重新加载),不能残留 A 的 PID。

### 2.2 【P1】终端 `pending_line` 没有上限,无换行的输出会无界增长

- **位置**:`apps/fhdc-desktop/src/panels/shell.rs:169` `append_bytes`,以及字段 `pending_line`
- **现象**:执行 `cat /data/local/tmp/某个二进制文件`、`dd`、或者任何长时间不吐换行的命令时,内存一路涨,界面越来越卡,最后可能 OOM。旧实现有 `MAX_BUFFER_BYTES = 256KB` 兜底,这次重写把兜底只留给了 `tail`,漏了 `pending_line`。
- **原因**:行切分后,最后一段(`remainder`)会累积到 `pending_line` 里等下一个换行;只要不来换行,它就只增不减。裁剪循环只作用于 `self.tail`,完全没管 `pending_line`。

```rust
let remainder = split.next_back().unwrap_or_default().to_owned();
...
self.pending_line.push_str(&remainder);   // ← 没有上限
while self.tail.len() > MAX_TAIL_LINES || ... { ... }   // ← 只裁 tail
```

- **改法**:给 `pending_line` 一个上限,超了就"强制断行"推进 `tail`,让同一个裁剪逻辑接管:

```diff
+/// 单行未换行残留的上限:超过就强制断行,避免无换行输出撑爆内存。
+const MAX_PENDING_BYTES: usize = 64 * 1024;
```

```diff
         self.pending_line.push_str(&remainder);
+        // 没有换行的超长输出(如 cat 二进制):强制切一行推进 tail,交给下面的裁剪。
+        if self.pending_line.len() > MAX_PENDING_BYTES {
+            let mut cut = MAX_PENDING_BYTES;
+            while !self.pending_line.is_char_boundary(cut) {
+                cut -= 1;
+            }
+            let overflow = self.pending_line.split_off(cut);
+            let head = std::mem::take(&mut self.pending_line);
+            self.tail_bytes += head.len() + 1;
+            self.tail.push(head);
+            self.pending_line = overflow;
+        }
         // 超限时从最旧的行开始丢弃。
         while self.tail.len() > MAX_TAIL_LINES
```

`is_char_boundary` 的循环向下退,最差退 3 次(UTF-8 最长 4 字节),不会越界。

- **验收**:`hdc shell cat /system/etc/something.bin` 之类跑一分钟,内存应稳定在 256KB + 64KB 量级。

### 2.3 【P2】终端行距变成 8px,看起来像双倍行距

- **位置**:`apps/fhdc-desktop/src/panels/shell.rs`(新的 `show_rows` 渲染块)
- **现象**:同一屏能看到的日志行数比之前少三分之一左右,行与行之间有明显空隙。
- **原因**:旧实现是**一个**多行 `Label`,`\n` 只推进字体行高;新实现是**每行一个** `Label`,于是 `theme.rs` 里全局的 `item_spacing = [8.0, 8.0]` 生效,每行多出 8px。`TAIL_ROW_HEIGHT = 16.0` 看起来是按"字体行高 + 8px 间距"估的,所以滚动条大致对得上 —— 但视觉上每行确实多出一条空白。

- **改法**:在终端框架内把纵向间距清零,并把行高改回字体行高:

```diff
         frame.show(ui, |ui| {
             ui.style_mut().override_text_style = Some(egui::TextStyle::Monospace);
+            // 每行一个 Label,全局 8px 的 item_spacing 会把终端撑成双倍行距。
+            ui.spacing_mut().item_spacing.y = 0.0;
             let total_rows = self.tail.len() + usize::from(!self.pending_line.is_empty());
```

```diff
-/// 回显行高(等宽字体,单行不换行)。
-const TAIL_ROW_HEIGHT: f32 = 16.0;
+/// 回显行高:与 Monospace 的字体行高一致(间距已在布局里清零)。
+const TAIL_ROW_HEIGHT: f32 = 15.5;
```

> 顺带:hilog 面板的 `ROW_HEIGHT = 17.0` 是同样的估法,同样吃了全局 8px 间距。改法相同,建议两处一起统一。

### 2.4 【P2】终端尾部裁剪用 `Vec::remove(0)`,到上限后每行 O(n)

- **位置**:`apps/fhdc-desktop/src/panels/shell.rs:187`
- **现象**:终端跑满 5000 行之后,每来一行都要把整个 `Vec` 前移一次;高频输出时这一段会占掉可观的时间。
- **原因**:`Vec::remove(0)` 是 O(n) 的 `ptr::copy`。

```rust
while self.tail.len() > MAX_TAIL_LINES || ... {
    let dropped = self.tail.remove(0);   // ← 每次搬 5000 个 String 头
    self.tail_bytes -= dropped.len() + 1;
}
```

- **改法**:换成 `VecDeque<String>`,丢弃用 `pop_front()`;渲染处把 `self.tail[index]` 改成 `self.tail.get(index)`,`display_text` 用 `self.tail.iter().map(String::as_str).collect::<Vec<_>>().join("\n")`。改动 5 处左右,语义不变。

### 2.5 【P2】hilog 切设备后出现"幻影空行"

- **位置**:`apps/fhdc-desktop/src/panels/hilog.rs:127` `reset_for`
- **现象**:切设备后日志区先出现一大片空白、滚动条很长,等新的日志进来才恢复正常。若该设备日志迟迟不来(或用户点过「停止」),这片空白会一直在。
- **原因**:`reset_for` 清了 `lines`(`self.lines.clear()`),但本轮新增的 `visible` 索引缓存和 `applied_filter` 键**都没清**。键里的 `data_generation` 也没变,于是 `show()` 认为缓存有效,`visible_len` 还是旧值(比如 800),而 `self.lines.get(idx)` 全部返回 `None`,渲染出 800 个空行。

- **改法**:和「清空」按钮做同一套失效:

```diff
         self.lines.clear();
         self.pending.clear();
         self.utf8 = super::Utf8Accumulator::new();
+        // 可见索引缓存也要失效,否则会按旧的行数渲染出一片空行。
+        self.visible.clear();
+        self.applied_filter = None;
+        self.data_generation += 1;
         self.error = None;
```

### 2.6 【P2】文件面板切目录瞬间仍显示上一个目录的内容

- **位置**:`apps/fhdc-desktop/src/panels/files.rs:202` `navigate`
- **现象**:双击进目录后,大约 100–300ms 内列表还是**旧目录**的行,然后才整体换成新目录。
- **原因**:本轮给文件列表也加了 `sorted_cache`,失效键是 `entries_generation`。`navigate()` 清了 `entries` 但没有让缓存失效,于是 `show()` 的键没变、继续借用旧缓存。`reset_for` 是清了的,只有"目录间跳转"这条路径漏了。

```rust
fn navigate(&mut self, path: RemotePath) -> Option<BackendCommand> {
    self.path = Some(path.clone());
    self.entries.clear();      // ← 数据清了,缓存没清
    self.reload(&Some(path))
}
```

- **改法**:

```diff
     fn navigate(&mut self, path: RemotePath) -> Option<BackendCommand> {
         self.path = Some(path.clone());
         self.entries.clear();
+        // 同时失效排序缓存:否则新目录数据到达前会继续画上一个目录的行。
+        self.sorted_cache.clear();
+        self.sort_cache_key = None;
         self.reload(&Some(path))
     }
```

> 更稳的做法:把 `entries_generation += 1` 收进一个 `invalidate_entries()` 小函数,所有改动 `entries` 的地方都调它,避免下次再加新路径时又漏。

### 2.7 【P3】发现进行中点「刷新设备」会被静默忽略

- **位置**:`apps/fhdc-desktop/src/runtime.rs`(`BackendCommand::RefreshDevices` 分支)
- **现象**:设备发现正在跑(最长 8 秒超时)时点刷新,什么都没发生,也没有任何提示。
- **改法**:二选一 —— 要么给按钮一个"发现中…"的反馈;要么把这次请求记下来,在 `Completion::Discovered` 处理完后补一次发现。

### 2.8 【P3】`tconn` 成功后最长约 4 秒才出现在设备列表

- **位置**:`apps/fhdc-desktop/src/runtime.rs`(`ConnectEndpoint` 分支)
- **现象**:界面上已经弹"连接成功",下拉框里还要等一下才出现。
- **原因**:连接成功后不再主动触发发现,完全依赖 2 秒轮询;而轮询又可能刚好碰上"发现进行中"被跳过一次,最坏约 4 秒。
- **改法**:连接任务成功后补一个 `Completion` 变体,让主循环立刻发起一次发现:

```rust
enum Completion {
    Transfer(OperationId),
    Discovered(Result<Vec<DeviceDescriptor>, BridgeError>),
    /// 连接/断开等改变了设备集合的操作完成,立刻重新发现。
    Rediscover,
}
```

主循环收到 `Rediscover` 且 `!discovery_in_flight` 时 `spawn_discovery`。

这一轮有两处改动只能在真机上确认,自动化测试覆盖不到:

### 3.1 概览改成 9 路并发 hdc 探测

`crates/fhdc-hdc/src/lib.rs` 的 `device_overview` 现在用 `tokio::join!` 同时发起 9 条 `hdc -t <key> shell ...`。

- **怎么测**:连真机,进概览页连续刷新 20 次,看字段是否齐全、有没有偶发空字段;再对比一次串行版本的总耗时(应当从约 2 秒降到 300ms 量级)。
- **万一不行**:退回"一次 shell 调用合并多条命令"的方案(`sh -c 'a; echo SEP; b; ...'`),只发一个进程。

### 3.2 设备端列表脚本的控制字符

沿用上一轮的结论:脚本已改成 FS(0x1C)+ RS(0x1E)+ 八进制,风险从"NUL 被吞"降到"控制字符能否穿过 `hdc shell` 输出"。

```powershell
hdc -t <key> shell "sh -c '<LIST_SCRIPT 原文>' fhdc-files /data/local/tmp" | Format-Hex
```

看是否真出现 `0x1C` / `0x1E`。**这一条从第一轮起就挂着,建议这次真机连上时顺手做掉** —— 如果控制字符被 hdc 规范化掉,文件面板在真机上就是空列表,而假后端永远测不出来。

### 4.1 `strip_ansi` 跨块的残留风险(说明)

增量解码器解决了 UTF-8 被切断的问题,但 ANSI 转义序列仍可能被切断:如果 `\x1b[32m` 的 `\x1b` 和 `[32m` 落在两个分片里,清洗器会把 `[32m` 当普通文本输出。

彻底做法是把 `strip_ansi` 从"对整段重新扫"改成"带状态的流式过滤":

```rust
/// 返回(可直接显示的文本, 待续接的转义尾巴)
fn strip_ansi_stream(pending: &mut String, input: &str) -> String
```

判断规则:文本结尾若停在 `\x1b`、`\x1b[`、或 OSC 未闭合,就把这一段留在 `pending` 里,下个分片拼上再处理。改动集中在 `shell.rs` 一个函数,可以配 3–4 个单测(切在 ESC、切在 CSI 参数、切在 OSC)。
