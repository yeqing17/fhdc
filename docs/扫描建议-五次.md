## 2. 本轮新发现

### 2.1 【P1】ANSI 清洗的"畸形保险"把小输出也一起短路了

- **位置**:`apps/fhdc-desktop/src/panels/shell.rs:473-483`
- **现象**:终端里凡是一次输出超过 4KB 的命令,输出中的转义序列不再被清除,屏幕上出现 `[32m`、`[0m` 这类字面量;同时 CRLF 也不再归一,每行尾部会多带一个 `\r` 控制字符。小于 4KB 的输出一切正常 —— 所以看起来像是"时好时坏"。
- **原因**:判断写在了合并后的 `source` 上,而不是只看残留的 `pending`:

```rust
fn strip_ansi_stream(pending: &mut String, input: &str) -> String {
    let mut source = std::mem::take(pending);
    source.push_str(input);                       // ← source = 上一块残留 + 本块输入
    // 注释说的是"待续接的尾巴超过上限"……
    if source.len() > ANSI_PENDING_LIMIT {        // ← 实际量的是 source(4096)
        output.push_str(&source);
        *pending = String::new();
        return output;                            // ← 本块输入整段按字面量放行
    }
```

而实际的输入规模是这样的:

| 环节 | 大小 | 位置 |
| --- | --- | --- |
| 单次 `read` 分片 | 8192 字节 | `crates/fhdc-hdc/src/shell.rs` `CHUNK_BYTES = 8 * 1024` |
| 合并窗口上限 | 65536 字节 | `runtime.rs` `COALESCE_MAX_BYTES = 64 * 1024` |
| 本条保险阈值 | 4096 字节 | 本轮新增 `ANSI_PENDING_LIMIT` |

阈值比单块分片还小一半,比合并上限小 16 倍。也就是说:**只要终端输出跑得快到能把 8KB 管道缓冲填满(或者 8ms 内攒够 4KB),每个事件都会命中这条"保险"**,`strip_ansi_stream` 直接原样返回。

只有输出细碎、每块都小于 4KB 时(手敲命令、小目录 `ls`)才走正常的清洗路径 —— 这正好是最不需要清洗的场景。

另外两个连带影响:

- CRLF 归一也在这段短路里,所以大块输出里每个 `\r` 都会原样留下,行尾带控制字符;
- 新增的单测 `flushes_degenerate_escape_as_literal` 断言的是"5002 字符整段吐出",等于把错误语义固化成了预期,改代码时必须同步改这个测试(见 2.2)。

- **改法**:只对**残留尾巴**做保险,新鲜输入无论多长都照常清洗。改动很小 —— 在合并之前先把超限的 pending 放行掉:

```diff
 fn strip_ansi_stream(pending: &mut String, input: &str) -> String {
+    let mut output = String::with_capacity(input.len() + 16);
+    // 保险只针对"跨块残留的畸形转义":尾巴本身超限才放弃续接。
+    // 不能拿 input 一起量 —— 单块分片是 8KB,合并后最大 64KB。
+    if pending.len() > ANSI_PENDING_LIMIT {
+        output.push_str(&std::mem::take(pending));
+    }
     let mut source = std::mem::take(pending);
     source.push_str(input);
-    // 畸形转义保险:待续接的尾巴超过上限(终止符迟迟不来,cat 二进制
-    // 常见),放弃续接按字面量吐出,避免 pending 无界增长并吞掉显示。
-    let mut output = String::with_capacity(source.len());
-    if source.len() > ANSI_PENDING_LIMIT {
-        output.push_str(&source);
-        *pending = String::new();
-        return output;
-    }
     let chars: Vec<char> = source.chars().collect();
```

这样:正常大块输出走完整清洗;只有当某个转义序列真的跨了很多块还没终止,pending 才会涨过 4096 并被放行。

- **验收**:
  1. 在终端里跑一条会产生大量彩色输出的命令(例如 `hilog` 或 `ls -R /system`),屏幕上不应出现 `[3Xm` 之类的字面量;
  2. 跑 `cat` 一个二进制文件,不应卡死或吞输出;
  3. 两种情况下行尾都不应出现多余控制字符。

### 2.2 【P3】修 2.1 时要同步调整新增的单测

- **位置**:`apps/fhdc-desktop/src/panels/shell.rs` `flushes_degenerate_escape_as_literal`
- **现状**:该测试构造 `"\x1b[" + 3000×';'`,第一次调用期望返回空;第二次再压 2000×';',期望"整段 5002 字符被吐出"。
- **按 2.1 修完之后**,第二次调用会正常进入扫描:`\x1b[` 后面全是 `;`(0x3B,不是 0x40–0x7E 的终止字节),扫描到结尾仍不完整,于是 `pending` 变成 5002 字符、返回空。要到**第三次**调用才会因为 `pending > 4096` 被放行。
- **建议**:把测试改成三段式(积累 → 仍不完整 → 下一次触发放行),断言 `pending` 在第二段后是 5002、第三段返回 5002 个字面量。这样测试语义和注释就对齐了。

### 2.3 【P3】hilog 在没有日志时高度塌成一条细边

- **位置**:`apps/fhdc-desktop/src/panels/hilog.rs`(frame 提到外面之后)
- **现象**:刚切到日志页、还没收到任何行时,日志区只有一个 12px 左右高的空条(`inner_margin(6.0)` 的两倍),要等第一行进来才撑开。
- **对比**:终端面板有 `ui.set_min_height(160.0)` 兜底,空状态会占住一块区域并显示"等待输出…";日志面板没有。
- **改法**:在 `visible_len == 0` 时给一个最小高度 + 提示文案,和终端保持一致。纯观感,可以顺手做。

### 2.4 【NIT】修完 2.1 之后,`Vec<char>` 的分配会重新暴露

- 上一轮 2.7 提过 `strip_ansi_stream` 每块都 `source.chars().collect::<Vec<char>>()`。因为 2.1 的短路,大于 4KB 的块根本没走到这行,所以现在**实际上没付出这笔开销**;一旦按 2.1 修好,64KB 的合并事件就会变成一次 256KB 的 `Vec<char>` 分配 + 逐字符扫描。
- 建议在修 2.1 的同时把它改成按 `&str` + `char_indices()` 走字节偏移,或者至少接受这个开销并留个注释。不改也能跑,只是每秒几十次的临时分配。
